# Modelo C4

Este documento descreve a arquitetura da Oficina API com o [modelo C4](https://c4model.com/), do nível mais amplo (contexto) ao mais detalhado (código). Os diagramas usam Mermaid e são renderizados diretamente no GitHub. As versões exportadas estão em [imagens/](imagens/) e consolidadas em [diagramas-arquitetura.pdf](diagramas-arquitetura.pdf).

## Legenda

| Cor | Elemento C4 |
|-----|-------------|
| Azul escuro | Pessoa (ator humano) |
| Azul médio | Sistema de software em foco |
| Azul | Contêiner (aplicação ou banco que roda de forma independente) |
| Azul claro | Componente (agrupamento de código dentro de um contêiner) |
| Cinza | Elemento externo ao escopo do diagrama |
| Borda tracejada | Fronteira (sistema, contêiner ou módulo) |

Cada caixa traz o nome, o tipo do elemento entre colchetes e uma descrição curta. Cada seta traz a intenção da interação e, entre colchetes, a tecnologia usada.

## Nível 2: Diagrama de Contêineres

Abre o sistema e mostra as unidades que rodam de forma independente. A aplicação é um monólito: um único processo Node.js concentra todas as APIs. O seed é um script separado, executado antes da API subir, que aplica as migrations pendentes e garante a existência do usuário administrador.

## Nível 3: Diagrama de Componentes

### Visão por módulos (bounded contexts)

Abre o contêiner da API. Cada módulo NestJS corresponde a um contexto de negócio e é dividido internamente nas camadas domain, application, infrastructure e interface (ver [camadas.md](camadas.md)). O módulo de Ordens de Serviço é o núcleo e consome os demais contextos apenas por portas.

O pipeline HTTP encaminha cada rota ao controller do seu módulo (`/api/auth`, `/api/clientes`, `/api/veiculos`, `/api/servicos`, `/api/pecas`, `/api/ordens-servico` e `/api/acompanhamento`). Todos os módulos usam o núcleo compartilhado e persistem no PostgreSQL pelos seus próprios repositórios TypeORM. Para manter o diagrama legível, essas setas repetitivas aparecem apenas a partir do núcleo.

<!-- diagrama: c4-3a-componentes-modulos -->
```mermaid

    cliente["<b>Cliente</b><br/><i>[Pessoa]</i>"]
```

### Núcleo: módulo Ordens de Serviço

Detalha o módulo central em portas e adaptadores. Os casos de uso dependem apenas de interfaces (portas). As implementações concretas ficam na infraestrutura: o repositório TypeORM do agregado e os adaptadores que traduzem os modelos dos outros contextos para o modelo do núcleo, funcionando como camada anticorrupção.

As linhas pontilhadas ligam cada porta (interface) à implementação concreta na infraestrutura. Os repositórios obtêm o `EntityManager` da transação corrente a partir do `ContextoDeTransacao`, por isso participam automaticamente da transação aberta pelo caso de uso.

<!-- diagrama: c4-3b-componentes-ordens-servico -->
```mermaid
flowchart TB
    equipe["<b>Equipe da oficina</b><br/><i>[Pessoa]</i>"]
    cliente["<b>Cliente</b><br/><i>[Pessoa]</i>"]

    subgraph modulo["Módulo ordens-servico"]
        ctrl["<b>OrdensServicoController</b><br/><i>[interface: controller REST, protegido por JWT]</i><br/><br/>/api/ordens-servico: criar, listar, detalhar,<br/>diagnóstico, itens, orçamento, finalizar,<br/>entregar e métricas de tempo médio"]
        pub["<b>ConsultaPublicaController</b><br/><i>[interface: controller REST, público]</i><br/><br/>GET /api/acompanhamento/{codigo}<br/>POST .../orcamento/aprovar e .../rejeitar<br/>(código da OS e CPF/CNPJ do cliente)"]
        uc["<b>Casos de uso</b><br/><i>[application]</i><br/><br/>Comandos, cada um em uma transação e com<br/>a OS lida com bloqueio: CriarOrdemDeServico<br/>(por CPF/CNPJ e placa), IniciarDiagnostico,<br/>AdicionarServico, AdicionarPeca, EnviarOrcamento,<br/>AprovarOrcamento, RejeitarOrcamento,<br/>FinalizarOrdem, EntregarVeiculo<br/><br/>Decisão pública: AprovarOrcamentoPeloCliente e<br/>RejeitarOrcamentoPeloCliente, verificados pelo<br/>LocalizadorDeOrdemDoCliente<br/><br/>Consultas: ListarOrdens, DetalharOrdem,<br/>CalcularTempoMedio, ConsultarAndamento"]
        agregado["<b>Agregado OrdemDeServico</b><br/><i>[domain: raiz de agregado]</i><br/><br/>ItemServico, ItemPeca, Orcamento,<br/>Aprovacao, StatusOrdemServico<br/>(máquina de estados) e eventos"]
        repoPorta["<b>OrdemDeServicoRepository</b><br/><i>[domain: porta de repositório]</i>"]
        portas["<b>Portas de saída</b><br/><i>[application: interfaces]</i><br/><br/>CatalogoDeServicos, GestaoDeEstoque,<br/>ConsultaDeCliente, ConsultaDeVeiculo<br/>e UnidadeDeTrabalho (shared)"]
        repoImpl["<b>OrdemDeServicoRepositoryTypeorm</b><br/><i>[infrastructure: repositório TypeORM]</i><br/><br/>Mapper e entidade ORM. Itens, histórico<br/>e aprovação gravados em colunas JSON.<br/>buscarPorIdParaAtualizar: SELECT ... FOR UPDATE"]
        adapters["<b>Adaptadores entre contextos</b><br/><i>[infrastructure: camada anticorrupção]</i><br/><br/>CatalogoDeServicosAdapter, GestaoDeEstoqueAdapter,<br/>ConsultaDeClienteAdapter, ConsultaDeVeiculoAdapter"]
    end

    uow["<b>UnidadeDeTrabalhoTypeorm</b><br/><i>[shared: com ContextoDeTransacao]</i><br/><br/>Abre a transação e publica o<br/>EntityManager no AsyncLocalStorage"]
    outros["<b>Repositórios de Clientes, Veículos,<br/>Serviços e Peças</b><br/><i>[outros módulos]</i><br/><br/>A baixa de estoque lê as peças com<br/>SELECT ... FOR UPDATE, em ordem de id"]
    db[("<b>Banco de dados</b><br/><i>[PostgreSQL 16]</i>")]

    equipe -- "<i>[HTTP/JSON, Bearer JWT]</i>" --> ctrl
    cliente -- "<i>[HTTP/JSON]</i>" --> pub
    ctrl --> uc
    pub -- "Consulta e decisão<br/>do cliente" --> uc
    uc -- "Aplica as regras<br/>de negócio" --> agregado
    uc -- "Carrega e salva<br/>o agregado" --> repoPorta
    uc -- "Consulta outros contextos,<br/>baixa estoque e abre transação" --> portas
    repoPorta -. "implementada por" .- repoImpl
    portas -. "implementadas por" .- adapters
    portas -. "implementada por" .- uow
    adapters -- "Traduzem para o<br/>modelo do núcleo" --> outros
    repoImpl -- "<i>[SQL]</i>" --> db
    outros -- "<i>[SQL]</i>" --> db
    uow -- "BEGIN, COMMIT<br/>ou ROLLBACK" --> db
```

## Nível 4: Código

O nível de código do núcleo está documentado nos diagramas de DDD, que refletem as classes do domínio:

- [Modelo de domínio](../ddd/diagramas.md#modelo-de-domínio): agregados, entidades, objetos de valor e referências por identidade.

## Diagrama de Implantação

Mostra como os contêineres são executados no ambiente local definido pelo `docker-compose.yml`. A imagem da API é construída em dois estágios (`Dockerfile`): o primeiro compila o TypeScript e o segundo leva apenas o JavaScript compilado e as dependências de produção.

<!-- diagrama: c4-implantacao -->
```mermaid
flowchart TB
    browser["<b>Navegador ou cliente HTTP</b><br/><i>[Swagger UI, curl, Postman]</i><br/><br/>Na própria máquina local"]

    subgraph host["Máquina local  [Nó: macOS, Linux ou Windows]"]
        subgraph compose["Docker Engine e Docker Compose  [Nó: docker-compose.yml]"]
            subgraph cApi["oficina-api  [Contêiner Docker: node:22-alpine]"]
                seedI["<b>Seed do administrador</b><br/><i>node dist/database/seeds/run-seed.js</i><br/><br/>Executa primeiro: aplica as migrations<br/>e cria o admin (idempotente)"]
                apiI["<b>API REST</b><br/><i>node dist/main.js</i><br/><br/>Porta 3000, NODE_ENV=production"]
            end
            subgraph cDb["oficina-db  [Contêiner Docker: postgres:16-alpine]"]
                dbI[("<b>PostgreSQL</b><br/><i>banco oficina</i><br/><br/>Porta 5432<br/>Healthcheck pg_isready")]
```

Variáveis de ambiente relevantes, definidas no `docker-compose.yml`: `DB_HOST=db`, `DB_MIGRATIONS_RUN=true` (as migrations pendentes são aplicadas na subida), `DB_SYNCHRONIZE=false`, `JWT_SECRET`, `JWT_EXPIRES_IN`, `ADMIN_EMAIL` e `ADMIN_PASSWORD`. Com `NODE_ENV=production`, a aplicação recusa subir sem `JWT_SECRET` e `ADMIN_PASSWORD` definidos.
